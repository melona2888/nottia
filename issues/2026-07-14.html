GPT-Live와 ChatGPT Work, GPT-5.6, Meta Muse Image와 Muse Spark 1.1, Grok 4.5, Google Managed Agents, LeRobot 0.6까지. 이번 주 핵심은 모델 발표보다 “대화, 데스크톱, 이미지, 코드, 로봇이 하나의 실행면으로 붙는가”입니다.

  2. Meta는 Muse Image·Muse Video와 Muse Spark 1.1로 이미지 생성, 컴퓨터 사용, 장기 컨텍스트 에이전트 경쟁에 다시 들어왔습니다.

Editorial Note

이번 주 발표들은 서로 다른 회사 이야기처럼 보이지만 방향은 비슷합니다. AI는 채팅창 안의 답변기에서 벗어나 음성으로 대화하고, 파일을 만지고, 브라우저와 데스크톱을 조작하고, 장시간 작업을 이어 가는 실행 계층이 되고 있습니다. 그래서 앞으로 비교해야 할 것은 “누가 더 똑똑한가”만이 아니라 “얼마나 오래, 싸게, 감사 가능하게 끝까지 일하는가”입니다.

01 Icebreaker 선정 이유: 음성 UI 핵심 신호

GPT-Live, 음성 AI가 “차례 기다리기”를 줄인다

OpenAI는 7월 8일 GPT-Live를 공개했습니다. 핵심은 음성을 텍스트로 바꾸고 답을 만든 뒤 다시 읽어주는 파이프라인이 아니라, 듣고 말하는 과정을 동시에 다루며 필요하면 뒤에서 더 깊은 모델에 일을 맡기는 구조입니다.

Full-duplex 대화

GPT-Live는 입력을 계속 듣는 동안 출력도 만들 수 있습니다. 사용자가 잠깐 멈췄다고 대화가 끊기거나 갑자기 끼어드는 문제를 줄이는 방향입니다.

깊은 일은 위임

검색, 추론, 복잡한 작업이 필요하면 배후 모델에 넘기고, 음성 모델은 대화 흐름을 유지합니다. 목소리 UI와 에이전트 실행이 분리되는 신호입니다.

두 버전 출시

GPT-Live-1과 GPT-Live-1 mini가 ChatGPT 사용자에게 글로벌 롤아웃을 시작했고, API 제공도 예고됐습니다.

음성이 작업 입구가 됨

단순 낭독보다 중요한 변화는 음성으로 장시간 작업을 시작하고 중간에 방향을 바꿀 가능성입니다. 회의, 상담, 학습 앱이 바로 영향을 받습니다.

02 Main 선정 이유: 프런티어 모델 출시

GPT-5.6, Sol·Terra·Luna로 성능과 비용을 층으로 나눈다

OpenAI는 7월 9일 GPT-5.6 family를 일반 공개했습니다. Sol은 flagship, Terra는 일상 작업용 균형 모델, Luna는 가장 저렴한 모델로 배치되어 “하나의 최고 모델”보다 작업 난이도와 원가에 맞춘 선택지를 전면에 둡니다.

세 가지 티어

Sol, Terra, Luna가 ChatGPT, Codex, OpenAI API에 들어갑니다. Free와 Go 사용자는 ChatGPT Work와 Codex에서 Terra를 쓰는 구조입니다.

Max와 Ultra

max는 더 긴 추론 시간을 주고, ultra는 기본적으로 병렬 에이전트를 조율합니다. 비싼 추론을 “필요한 일에만 켜는 모드”로 제품화한 셈입니다.

Programmatic Tool Calling

Responses API에서 모델이 중간 데이터를 프로그램으로 처리하고 필요한 것만 남길 수 있습니다. 긴 도구 호출 흐름의 토큰 낭비를 줄이는 기능입니다.

토큰 가격 공개

Sol은 1M tokens당 입력 5달러·출력 30달러, Terra는 2.5달러·15달러, Luna는 1달러·6달러입니다. 캐시 write/read 정책도 함께 바뀌었습니다.

02 Main 선정 이유: 업무 에이전트 제품화

ChatGPT Work, 답변이 아니라 완성물을 맡는 에이전트로 간다

ChatGPT Work는 앱과 파일을 가로질러 정보를 모으고, 몇 시간짜리 프로젝트를 작은 단계로 쪼개며, 문서·슬라이드·시트·웹앱 같은 완성물을 만드는 제품으로 소개됐습니다. Codex 기술이 업무 표면으로 넘어온 사례입니다.

앱과 파일을 넘나듦

Slack, Notion, Microsoft 365, Google Drive 같은 업무 맥락을 가져와 결과물을 만드는 흐름이 강조됐습니다. 질문 답변보다 자료 조립과 실행에 가깝습니다.

몇 시간짜리 프로젝트

복잡한 일을 단계로 나누고 독립적으로 진행할 수 있다는 점이 전면에 나옵니다. 사용자는 진행 상황을 보고, 질문에 답하고, 중요한 행동을 승인합니다.

Scheduled Tasks

자리를 비운 동안 새 메시지를 문서나 슬라이드로 반영하고 변경점을 공유하는 예시가 제시됐습니다. 반복 업무 자동화와 연결됩니다.

비개발자 Codex

OpenAI는 매주 500만 명 이상이 Codex를 쓰고, 그중 100만 명 이상은 소프트웨어 개발 밖의 업무에 쓴다고 설명합니다. 에이전트가 직무 도구가 되는 신호입니다.

02 Main 선정 이유: 생성 이미지 제품 경쟁

Meta Muse Image, 이미지 생성도 도구를 쓰는 에이전트가 된다

Meta는 7월 7일 Muse Image와 Muse Video preview를 공개했습니다. Muse Image는 프롬프트를 곧장 이미지로 바꾸는 모델이 아니라, 검색과 코드 도구를 써서 사실성·구성·편집 정확도를 높이는 agentic image generation으로 설명됩니다.

도구 쓰는 이미지 모델

검색으로 현실 참조를 찾고, 코드로 플롯이나 QR code 같은 정확한 요소를 만들 수 있습니다. 이미지를 “그리는” 모델에서 “조립하고 확인하는” 모델로 이동합니다.

자기수정 루프

생성 중 작은 오류는 편집하고, 큰 오류는 새로 만들며, 필요하면 다른 도구를 호출합니다. inference-time compute를 더 쓰면 품질이 올라가는 구조입니다.

제품 표면 확대

Muse Image는 Meta AI app, meta.ai, 미국 Instagram Stories, 일부 국가 WhatsApp에서 제공됩니다. Facebook 지원도 예고됐습니다.

Content Seal

Meta AI에서 만든 이미지는 보이지 않는 watermark인 Content Seal을 포함합니다. detection tool preview도 함께 나와 출처 검증 흐름을 붙였습니다.

02 Main 선정 이유: 에이전트 모델 경쟁

Muse Spark 1.1과 Grok 4.5, 코딩 에이전트 경쟁을 속도와 원가로 끌고 간다

Meta의 Muse Spark 1.1과 xAI의 Grok 4.5는 둘 다 “agentic tasks, coding, knowledge work”를 전면에 둡니다. 벤치마크 숫자 경쟁보다 흥미로운 점은 장기 컨텍스트, subagent 조율, 컴퓨터 사용, token efficiency를 모델의 핵심 상품성으로 삼는다는 것입니다.

100만 토큰 맥락

Muse Spark 1.1은 1M token context window를 관리하고, 오래전 작업에서 필요한 정보를 회수·압축한다고 설명합니다. 긴 프로젝트 유지력이 경쟁 포인트입니다.

컴퓨터 사용 판단

Muse Spark 1.1은 스크립트가 빠른지, 직접 클릭이 나은지 판단하도록 훈련됐다고 합니다. UI 조작과 자동화가 한 모델 안에서 만납니다.

Grok 4.5의 속도 주장

xAI는 Grok 4.5를 80 TPS로 제공하고, SWE Bench Pro task에서 Opus 4.8 max보다 평균 출력 token이 4.2배 적었다고 제시합니다.

가격이 메시지

Grok 4.5 가격은 1M tokens당 입력 2달러·출력 6달러입니다. xAI는 Grok Build, Cursor, API console에서 사용 가능하다고 밝혔습니다.

03 Dev 선정 이유: 에이전트 API 운영면

Gemini API Managed Agents, 에이전트를 오래 실행하는 서버 작업으로 다룬다

Google은 7월 7일 Gemini API의 Managed Agents에 background execution, remote MCP server integration, custom function calling, credential refresh를 추가했습니다. 에이전트를 HTTP 요청 하나에 묶인 응답기가 아니라, 재접속하고 상태를 확인하는 비동기 작업자로 보는 업데이트입니다.

Background true

긴 작업은 서버에서 비동기로 돌리고, 클라이언트는 ID로 상태를 polling하거나 stream을 다시 붙일 수 있습니다. 장시간 에이전트 UX의 기본 부품입니다.

Remote MCP

사설 DB나 내부 API를 proxy로 감싸는 대신 remote MCP server를 직접 연결할 수 있습니다. 기업 도구 연결이 공식 API 표면으로 올라옵니다.

Custom functions

서버 sandbox 도구는 자동 실행하고, 로컬 비즈니스 로직은 requires_action으로 넘겨 클라이언트가 실행합니다. 권한 경계가 더 분명해집니다.

Credential refresh

짧은 수명의 토큰과 network rule을 기존 environment_id에 갱신할 수 있습니다. 파일 상태를 유지한 채 연결 조건만 바꾸는 운영 패턴입니다.

Google: Managed Agents in Gemini API

GitHub Changelog에는 7월 9일 OpenAI GPT-5.6 Sol, Terra, Luna의 Copilot 제공과 “Ask Copilot for a repository overview”가 같이 올라왔습니다. 모델 선택과 코드베이스 요약이 개발자 도구 안의 기본 기능으로 붙는 흐름입니다.

GPT-5.6 in Copilot

Repository overview

새 repo에 들어갔을 때 Copilot에게 구조와 역할을 요약하게 하는 기능입니다. 온보딩과 코드리뷰의 첫 10분을 줄이는 성격입니다.

7월 8일에는 GitHub Mobile에서 Copilot CLI session 알림과 conflict 처리 개선도 올라왔습니다. 에이전트 진행 상황을 모바일에서 보는 흐름입니다.

품질과 보안이 함께 감

03 Dev 선정 이유: 로봇 학습 루프

LeRobot 0.6.0, 로봇이 실패하면 다시 데이터가 되는 루프를 만든다

Hugging Face의 LeRobot v0.6.0은 로봇 모델, 평가, 데이터, 배포 CLI를 한 번에 크게 확장했습니다. 제품 관점에서 핵심은 “정책 실행, 실패 감지, 사람 개입, 데이터 축적, 재학습”이 한 도구 체인 안으로 들어온다는 점입니다.

World model policies

VLA-JEPA, LingBot-VA, FastWAM 같은 정책이 미래를 상상하며 학습하는 흐름을 LeRobot 안으로 들였습니다.

Reward models API

Robometer와 TOPReward로 로봇이 성공했는지 점수화하는 인터페이스가 생겼습니다. 행동 데이터 품질을 자동으로 읽는 기반입니다.

lerobot-rollout

배포 전용 CLI가 생겼고, sentry·highlight·dagger 같은 전략을 제공합니다. 실패 순간을 놓치지 않고 다시 데이터로 만드는 설계입니다.

여섯 개 시뮬레이션 벤치

RoboTwin 2.0, RoboCasa365, RoboCerebra, RoboMME 등 새 benchmark family가 lerobot-eval 아래 붙었습니다. 로봇 에이전트도 평가 도구가 제품화됩니다.

Hugging Face: LeRobot v0.6.0
04 Research 선정 이유: 제품 뒤의 연구 흐름

이번 주 연구 노트: 오래 기억하고, 도구를 고르고, 더 싸게 서빙하기

이번 주 arXiv 후보들은 에이전트를 실제로 굴릴 때 부딪히는 문제를 많이 다룹니다. 긴 문맥에서 근거를 찾는 법, 계속 배우는 조건, 배포 후 RL 시스템, 많은 도구 중 선택하는 retriever, vLLM 설정의 비용·정확도 trade-off가 핵심입니다.

Self-Guided TTT

긴 문맥 전체가 아니라 질문에 필요한 evidence span만 골라 test-time training을 합니다. LongBench 계열에서 최대 15% 상대 개선을 보고했습니다. arXiv

Continual learning의 조건

새 도메인, 시간에 따른 사실 변화, 에이전트 상태 누적을 나누어 봅니다. 언제 context 관리로 충분하고 언제 모델 업데이트가 필요한지 묻습니다. arXiv

Self-evolving agents

운영 중인 에이전트가 자기 경험에서 배우려면 trajectory data protocol, governed data proxy, evolution control plane이 필요하다고 주장합니다. arXiv

PORTS tool selection

도구가 많아질수록 무엇을 불러야 할지 고르는 retriever가 중요합니다. LLM preference signal로 tool retriever를 맞추는 접근입니다. arXiv

vLLM 설정도 정확도에 영향

attention kernel, prefix caching, chunked prefill 조합을 9,000회 실험해 에너지, 지연, 정확도 trade-off를 봅니다. serving 옵션도 결과 품질에 영향을 줄 수 있다는 점이 포인트입니다. arXiv
