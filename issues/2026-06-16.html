개인 맥락을 읽는 비서

Anthropic Fable·Mythos, 공개보다 차단이 더 큰 뉴스가 됐다

모델 접근권이 정책 리스크

사이버 방어와 공격의 같은 도구

초강력 모델의 새 출시 조건

OpenAI와 Anthropic을 둘러싼 상장 기대 보도는 투자 뉴스 그 자체보다 AI 회사의 전략을 읽는 렌즈로 중요합니다. 수익성, 가격, 규제, 클라우드 의존도, 기업 고객 유지가 모델 성능만큼 큰 평가 항목이 됐습니다.

성능보다 반복 매출

안전 발언과 배포 속도

두 회사 모두 빠른 발전의 위험을 말하면서도 더 강한 제품을 내고 있습니다. 독자는 메시지보다 실제 출시, 접근 제한, 위험 보고의 일관성을 봐야 합니다.

02 Main 선정 이유: OpenAI 제품 전략

Codex는 코딩 도구에서 장기 실행 작업면으로 커진다

OpenAI의 Codex 관련 보도는 코딩 AI가 "파일을 고치는 챗봇"을 넘어 오래 켜져 있는 작업 환경으로 가고 있음을 보여줍니다. Ona 인수 추진과 ChatGPT·Codex 통합 방향은 같은 신호입니다.

ChatGPT 안으로 들어가는 개발

Codex를 일반 사용자용 assistant 흐름과 결합하려는 방향이 보도됐습니다. 코딩 기능은 개발자 전용 제품이 아니라 문서, 예약, 자동화 같은 생활형 작업과 이어집니다.

02 Main 선정 이유: loop engineering

AI loop engineering, 에이전트를 한 번 답하게 하지 않고 계속 고치게 한다

이번 주 에이전트 논의의 공통어는 루프입니다. 계획, 실행, 관찰, 평가, 재시도를 구조화해야 AI가 즉흥 답변을 넘어 반복 가능한 작업 시스템이 됩니다.

코드는 결과물이 아니라 도구

agentic engineering 논의는 LLM이 판단 루프를 돌리고 코드는 임시 도구처럼 생성·폐기된다고 봅니다. 개발자는 모든 줄을 쓰기보다 루프의 목적과 검증 기준을 설계합니다.

즉석 실행의 취약함

AI Workflow Store 논문은 매번 새로 만든 도구 체인보다 검증된 워크플로를 재사용해야 한다고 주장합니다. 반복 사용되는 작업일수록 테스트와 배포 단계를 루프 안에 넣어야 합니다.

긴 작업은 기억 구조가 필요

Arbor 연구는 가설, 증거, 산출물을 트리로 남겨 다음 시도에 반영합니다. 실패를 버리지 않고 다음 실행의 재료로 바꾸는 것이 루프 엔지니어링의 핵심입니다.

바이브 코딩의 다음 단계

아이디어를 말하면 앱이 나오는 흐름은 시작점일 뿐입니다. 실제 프로젝트에서는 요구사항, 테스트, 보안, 되돌리기 기준이 반복 루프에 들어가야 합니다.

03 Dev 선정 이유: 개발 흐름 변화

Microsoft·GitHub, intent-first 개발을 더 노골적으로 밀고 있다

Build 2026 보도에서 반복되는 표현은 code-first에서 intent-first로의 이동입니다. 사용자가 원하는 결과를 말하고, 에이전트가 코드를 만들며, 사람은 검토와 배포 조건을 관리하는 흐름입니다.

자동완성에서 작업 위임

Copilot Agent Mode와 데스크톱 앱 흐름은 여러 작업을 에이전트에게 나눠 맡기는 방향으로 설명됩니다. 초보자에게는 "어디서부터 고칠지" 부담이 줄어듭니다.

검토자는 여전히 사람

에이전트가 코드를 만들수록 테스트와 리뷰의 중요성은 줄지 않습니다. 결과를 병합하기 전 사람이 요구사항, 보안, 실제 동작을 확인해야 합니다.

여러 에이전트의 관제

작업이 길어지면 하나의 채팅창보다 대기열, 상태, sandbox, PR 단위 관리가 중요해집니다. 개발 도구의 UI도 에이전트 관제판처럼 바뀝니다.

운영 가능한 에이전트가 승부

앞으로의 차이는 모델 호출이 아니라 실패 복구, 권한, 로그, 비용 통제입니다. 작은 팀도 이 조건을 알아야 에이전트를 안전하게 씁니다.

03 Dev 선정 이유: loop runtime

Hermes Agent, 경험을 skill로 남기는 loop runtime 사례

Nous Research의 Hermes Agent는 GitHub 기준 약 194k stars를 가진 대형 agent 프로젝트입니다. 이번 호에서는 최신 급상승보다, agent가 기억·skill·cron·gateway를 묶어 반복 작업 루프를 만드는 공개 사례로 봅니다.

built-in learning loop

README는 경험에서 skill을 만들고, 사용 중 skill을 개선하고, 과거 대화를 검색한다고 설명합니다. loop engineering의 핵심인 "실패와 성공을 다음 실행에 남기는 구조"와 맞닿아 있습니다.

cron으로 반복 실행

Hermes는 자연어 기반 scheduled automation과 gateway를 내세웁니다. 에이전트가 한 번 답하고 끝나는 대신 정해진 시간마다 보고, 점검, 백업 같은 루프를 돌리는 형태입니다.

last30days와 같은 skill 호스트

last30days-skill의 Hermes setup 문서는 hermes skills install로 research skill을 설치하는 흐름을 안내합니다. Hermes는 brain/runtime, last30days는 그 위에 꽂는 research loop로 읽을 수 있습니다.

권한 검토가 병목

skill을 agent가 만들고 수정할 수 있으면 생산성은 커지지만 권한, 외부 API 키, 파일 접근, 실행 기록 검토가 중요해집니다. loop가 강해질수록 안전장치도 루프 안에 들어가야 합니다.

03 Dev 선정 이유: 컨텍스트 비용

Headroom류 도구, 에이전트의 병목이 토큰과 로그임을 보여준다

GitHub Trending에서 Headroom은 도구 출력, 로그, 파일, RAG chunk를 LLM에 넣기 전 압축하는 흐름으로 주목받았습니다. 에이전트가 길게 일할수록 컨텍스트 비용과 잡음 관리는 핵심 운영 문제가 됩니다.

로그가 너무 길다

테스트 로그와 검색 결과를 그대로 넣으면 모델은 비싸지고 느려집니다. 필요한 신호만 남기는 압축 계층이 에이전트 품질에 직접 영향을 줍니다.

RAG도 요약 품질 싸움

문서를 많이 가져오는 것보다 어떤 조각을 어떻게 줄여 넣는지가 중요합니다. 긴 컨텍스트가 있어도 구조화되지 않으면 판단이 흐려집니다.

MCP와 프록시 형태

Headroom은 라이브러리, 프록시, MCP server 형태를 내세웁니다. 에이전트 도구 체인 중간에 끼워 넣는 인프라형 접근입니다.

작업 루프의 비용 통제

루프가 반복될수록 토큰 낭비는 누적됩니다. 압축과 요약 정책은 작은 자동화에서도 예산과 속도를 좌우합니다.

이번 주 연구 노트: 에이전트를 오래 굴리는 방법

연구 흐름은 성능 숫자보다 반복 가능한 에이전트 운영에 가까워졌습니다. 루프, workflow reuse, hypothesis tree, skill evolution, self-mining이 공통 키워드입니다.

Agentic Engineering: 코드보다 루프

LLM이 추론 루프를 돌리고 코드는 임시 도구가 되는 패러다임을 정리합니다. 개발자의 역할이 작성자에서 검증자·루프 설계자로 이동하는지 봐야 합니다. arXiv

AI Workflow Store: 검증된 루프 재사용

즉석 생성 에이전트 대신 테스트된 workflow를 저장해 재사용하자는 제안입니다. 고위험 작업에서는 빠른 답보다 hardened workflow가 중요합니다. arXiv

Arbor: 가설 트리로 연구 누적

가설, 산출물, 증거, 교훈을 트리로 남겨 장기 연구 루프를 개선합니다. 실패 기록을 다음 실행의 검색 공간으로 바꾸는 점이 핵심입니다. arXiv

SkillChain: 생산 피드백으로 skill 진화

전자상거래 이미지 assistant에서 skill 생성, 라우팅, refinement를 연결합니다. 실제 서비스 로그를 skill 개선 루프로 넣는 사례로 볼 만합니다. arXiv

SIRI: 성공 궤적에서 skill을 내재화

에이전트가 자신의 성공 rollout에서 유용한 skill을 채굴하고 distillation하는 방식입니다. inference 때 별도 skill bank 없이 동작하려는 점이 배포 관점에서 중요합니다. arXiv
